# OpenSpec Integration Guide

This guide describes how to integrate Gherkin feature files generated by the
capability-to-gherkin skill into an **OpenSpec** specification-driven development workflow.

## Detecting OpenSpec

OpenSpec is present in a project when any of these are true:

- `openspec.yaml` or `openspec.yml` exists at the project root
- `.opspec/` directory exists
- `specs/` directory exists at the project root (OpenSpec default for spec files)

When OpenSpec is detected, the skill follows the OpenSpec workflow (Stage 5). When it is not
detected, `.feature` files are generated directly into a `features/` directory and OpenSpec
integration is reported as skipped.

## OpenSpec Workflow Commands

| Command | Purpose |
|---------|---------|
| `/opsx:propose` | Create a new specification change proposal |
| `/opsx:apply` | Implement the specification (create tasks, assign owners) |
| `/opsx:verify` | Validate implemented work against the specification |
| `/opsx:archive` | Archive the completed proposal and its specs |

## Integration Steps

### Step 1: Create a Proposal

```
/opsx:propose
Title: Add Gherkin specs for Customer Management capability
Description: Converts the Customer Management L1 capability and its L2 sub-capabilities
(Registration, Profile Management, Communication) from the capability map into executable
Gherkin Feature files. This bridges the legacy-capability-extractor domain model to BDD
test coverage.

Traceability:
- Original capability map: capability-output/a6-domain-model.md
- Capability IDs: BC-001 (Customer Onboarding), BC-002 (Account Management)
```

### Step 2: Place Feature Files in `specs/`

OpenSpec expects specification files in the `specs/` directory. Place each `.feature` file
there:

```
project-root/
├── specs/
│   ├── customer-management.feature
│   ├── order-processing.feature
│   └── customer-communication-outline.feature  # Scenario Outline
├── tasks.md
└── openspec.yaml
```

### Step 3: Update `tasks.md`

For each Feature, create tasks covering:

1. **Step definition stubs** — Create stubs for all Given/When/Then steps that have no
   existing definition. Tag with `@openspec` and link to the originating Feature.
2. **Test data setup** — Ensure Background and Given preconditions can be satisfied with
   test fixtures.
3. **Cross-capability scenarios** — If a Feature's Background depends on another capability,
   ensure that capability's Feature is also generated and the dependency is documented.

### Step 4: Link Back to the Capability Map

In the proposal description and in each Feature file's header comment, include a reference
to the original capability map entry:

```gherkin
# Traceability: legacy-capability-extractor a6-domain-model.md → BC-001 Customer Onboarding
# L2: Customer Registration (BC-001-01), Customer Profile Management (BC-001-02),
#     Customer Communication (BC-001-03)
```

### Step 5: Verify and Archive

When all scenarios have matching step definitions and tests pass:

```
/opsx:verify    # Validate scenarios against the specification
/opsx:archive   # Archive the proposal
```

## Best Practices for OpenSpec Integration

- **One proposal per L1 capability** — Keep proposals focused. A proposal for "Customer
  Management" should contain only the Customer Management Feature and its Scenarios.
- **Tags carry cross-tool metadata** — Use `@openspec` in addition to `@capability`,
  `@level1`, `@level2` so the OpenSpec system can identify skill-generated specs.
- **Scenario Outlines for variant behavior** — If a capability has rules that vary by
  input (e.g., communication channels), use `Scenario Outline` with `Examples:` rather than
  separate scenarios.
- **Background for shared setup only** — Do not put L2-specific preconditions in Background;
  they belong in individual Scenarios or in the OpenSpec task setup.
- **Step definition ownership** — When creating step-definition tasks, assign them to the
  team that owns the corresponding bounded context (from the capability map's L2 "Code
  Location" field).

## OpenSpec-Specific Anti-Patterns

| Anti-Pattern | Fix |
|-------------|-----|
| Feature files placed outside `specs/` | Move them to `specs/` so OpenSpec discovers them |
| Proposal created but `tasks.md` not updated | Add tasks for step definitions and test data |
| No traceability link to the capability map | Add `# Traceability:` comment in each Feature |
| Cross-capability dependency not documented | Add it as a task cross-reference in the proposal |
| Archiving without verifying scenarios pass | Always run `/opsx:verify` before `/opsx:archive` |
