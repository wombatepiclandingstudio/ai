# Scenario Generation Examples

This file illustrates the scenario patterns generated by the capability-to-gherkin skill for
each scenario type. Use these as reference when writing or reviewing Gherkin scenarios.

## 1. Happy Path

The standard, successful execution of a capability. Every L2 must have at least this.

```gherkin
@capability @level2 @order-creation @happy-path
Scenario: Order Placement — happy path
  Given a registered customer with items in their shopping cart
  When the customer submits the order
  Then the order should be created with status "pending"
  And a confirmation email should be sent to the customer
  And the inventory should be reserved
```

## 2. Alternative Flow

A valid but different path through the same capability.

```gherkin
@capability @level2 @order-creation @alternative
Scenario: Order Placement — with saved payment method
  Given a registered customer with items in their cart and a saved payment method
  When the customer submits the order using the saved payment method
  Then the order should be created with status "pending"
  And the payment should be processed using the saved method
  And a confirmation should be displayed without requiring additional input
```

## 3. Exception / Error

Error conditions and how the system handles them.

```gherkin
@capability @level2 @order-creation @exception
Scenario: Order Placement — insufficient inventory
  Given a registered customer with items in their cart
  When one item's inventory drops below the requested quantity
  Then the order should be rejected
  And an error message should explain which item is unavailable
  And the cart should remain intact for the customer to adjust
  And no payment should be attempted
```

## 4. Boundary / Edge

Minimum, maximum, or threshold values.

```gherkin
@capability @level2 @order-creation @boundary
Scenario Outline: Order Placement — quantity boundaries
  Given a registered customer with a single product in their cart
  When the customer orders a quantity of "<quantity>"
  Then <expected-behavior>

  Examples:
    | quantity | expected-behavior                          |
    | 1        | the order should proceed normally        |
    | 99       | the order should proceed with a warning   |
    | 100      | the order should be rejected as bulk      |
    | 0        | the order should be rejected as invalid   |
```

## 5. Cross-Capability

Exercises dependencies between capabilities (from the capability map's dependency map).

```gherkin
@capability @level2 @order-creation @cross-capability
Scenario: Order Placement — customer profile must exist
  Given a customer who has not yet completed profile setup
  When the customer attempts to place an order
  Then the order should be held for profile completion
  And the customer should be redirected to complete their profile
  And the original cart contents should be preserved
```

## Scenario Naming Conventions

- **Title format:** `<L2 Capability Name> — <flow type>`
- **Flow type suffix:** `happy path`, `error case`, `alternative flow`, `boundary values`,
  `cross-capability`
- **Scenario Outline titles:** Include the varying aspect, e.g.
  `Customer Communication — by channel preference`

## Tag Conventions

Every generated scenario carries at minimum:

- `@capability` — identifies skill-generated content
- `@level2` — identifies the granularity level
- `@<l2-tag>` — kebab-case descriptor of the L2 capability
- `@<flow-type>` — one of: `@happy-path`, `@alternative`, `@exception`, `@boundary`,
  `@cross-capability`

Features (L1) carry `@capability` and `@level1`.
